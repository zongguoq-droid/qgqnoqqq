# 智能车载终端 — 完整学习文档

## 项目概览

基于 i.MX6ULL (ARM Cortex-A7 528MHz / 512MB DDR3 / 4GB eMMC) 的智能车载终端。

**核心理念：多进程 + UNIX Socket + poll 事件驱动**。5 个独立进程（net_daemon 已移除，sensor_daemon 合并入 Qt SensorThread）通过本地 Socket 通信，每个进程单线程 poll 循环，全异步非阻塞 IO。EPOLL→POLL 切换是因为开发板内核 (4.9.88) 的 timerfd/signalfd 存在兼容问题，poll 是 POSIX 标准接口，通用性更好。

```
qt_ui (Qt 5.14) ←── UNIX Socket ──→ 4 个后台 C 进程
                                        │
                          ┌─────────────┼─────────────┐
                          │             │             │
                      guard_daemon  gps_daemon  input_daemon ...
                      (守护/重启)   (GPS定位)   (按键+LED)
                          │
                      canbus_daemon   av_daemon     dvr_daemon
                      (CAN总线)     (音频播放)    (行车录像)

温湿度: Qt SensorThread 直接读 /dev/mydht11 (不再走独立进程)
```

---

## 第 0 章：为什么这样设计？

### 多进程 vs 多线程

| 多进程 | 多线程 |
|--------|--------|
| 进程间天然隔离，一个模块崩溃不影响其他 | 一个线程崩溃整个进程挂掉 |
| 独立编译/调试/重启 | 需要整体调试 |
| 内存独立，无竞态条件 | 共享内存，需锁保护 |
| 适合学习（每个进程独立理解） | 调用链复杂 |

**选择多进程的原因：** 车载终端需要长期稳定运行。如果 GPS 模块进程崩溃，不会影响 DVR 录像。guard_daemon 会自动重启崩溃的进程。

### 为什么用 UNIX Socket 而不是共享内存？

- UNIX Socket 是全双工，双向通信（Qt UI 既能收数据也能发指令）
- 与网络 Socket API 完全一样，以后可以平滑迁移到网络通信
- 不需要额外的同步机制（共享内存需要信号量/互斥锁）
- Qt 原生支持 QLocalSocket

### 为什么用自定义二进制协议而不是 JSON？

| 二进制协议 | JSON |
|-----------|------|
| 解析开销极小（直接强转结构体） | 需要 JSON 解析器 |
| 数据量最小（GPS 数据约 40 字节） | 有字段名冗余 |
| 不依赖第三方库 | 需要 cJSON/json-c |
| 学习价值高（字节序/对齐/CRC） | 学习价值一般 |

在 528MHz 单核 CPU 上，每条消息节省的解析时间积累起来很可观。

## 第 1 章：common 公共库

### 1.1 log — 日志系统

**文件：** `src/common/log/log.h`, `log.c`

**核心知识点：**

1. **可变参数 `va_list`**：C 语言实现 `printf` 风格函数的基础
   ```c
   void log_write(const char *tag, log_level_t level,
                  const char *fmt, ...) {
       va_list args;
       va_start(args, fmt);
       vsnprintf(msg_body, sizeof(msg_body), fmt, args);
       va_end(args);
   }
   ```

2. **`localtime_r` vs `localtime`**：`_r` 后缀是 POSIX 线程安全版本。`localtime` 返回静态缓冲区指针，多线程同时调用会互相覆盖。

3. **日志轮转**：`rename()` 实现。同一文件系统内 `rename` 是原子操作，不会丢失数据。

4. **行缓冲模式 `_IOLBF`**：每行自动 flush。嵌入式 eMMC 上平衡了数据安全和闪存寿命——最多丢失一行日志，而不是等 8KB 缓冲满了才写。

5. **`pthread_mutex`**：保护多线程写日志时文件指针不交错。虽然是单线程项目，但养成好习惯。

### 1.2 crc8 — 校验算法

**文件：** `src/common/crc/crc8.h`, `crc8.c`

**核心知识点：**

1. **查表法 vs 逐位计算**：空间换时间的经典案例。256 字节查找表放在 `.rodata` 段（只读数据，不占 RAM），每个字节只需 1 次查表 + 1 次异或。

2. **CRC 分段计算**：CRC 算法支持分多次计算。对于长数据可以分块喂入，避免在栈上分配大缓冲区（嵌入式栈空间有限）。

3. **多项式 0x07**：`x^8 + x^2 + x + 1`。CRC-8 有 1/256 的误检率，配合帧头帧尾（1/65536 误识别概率），组合后误识别概率极低（1/16777216）。

### 1.3 ringbuffer — 环形缓冲区

**文件：** `src/common/ringbuffer/ringbuffer.h`, `ringbuffer.c`

**核心知识点：**

1. **取模优化**：容量向上取整为 2 的幂（`round_up_power_of_two`），取模运算 `%` 变为位运算 `& (capacity-1)`。Cortex-A7 没有硬件除法器，`%` 需要几十个周期，`&` 只需 1 个周期。

2. **回绕处理**：物理上是线性内存但逻辑上是环形的。当 `write_pos + len > capacity` 时需要分两段 `memcpy`。

3. **非覆盖写入**：空间不够时只写能容纳的部分，不覆盖未读数据。对于协议解析，丢失旧数据比覆盖新数据更安全。

4. **无锁设计**：单生产者（只写）+ 单消费者（只读）场景下，`read_index` 和 `write_index` 各只被一方修改，无需锁。

### 1.4 config — INI 配置文件解析

**文件：** `src/common/config/config.h`, `config.c`

**核心知识点：**

1. **`strtol` vs `atoi`**：`atoi("abc")` 返回 0（无法区分"0"和"解析失败"），`strtol("abc", &endptr, 10)` 可以通过 `endptr` 检测解析是否成功。

2. **`strcasecmp`**：POSIX 不区分大小写比较。Windows 上为 `_stricmp`。

3. **单向链表头插法**：新节点插入链表头部，O(1) 时间复杂度。配置项顺序不重要（查找是遍历）。

### 1.5 protocol — 二进制协议帧处理

**文件：** `src/common/protocol/protocol.h`, `protocol.c`

**核心知识点：**

1. **网络字节序 vs 主机字节序**：`htons()` 将 16 位整数从主机字节序转换为网络字节序（大端）。无论主机是大端还是小端，结果始终一致。

2. **有限状态机 (FSM)**：协议解析的经典模式。逐字节驱动，实现在流式数据中查找帧边界。本项目使用状态机而非 `sscanf`，因为状态机对格式错误更容错。

3. **粘包/断包处理**：TCP 是流式传输，没有消息边界。解决：帧头 + 帧长 + CRC + 帧尾，配合环形缓冲区缓存不完整数据。

4. **CRC 计算范围**：只计算可变部分（TYPE+LEN+DATA），不包含固定帧头 0xAA55。固定值包含在 CRC 中不会增加检错能力。

5. **每个连接独立解析器**：`protocol_parser_t` 实例化——Qt UI 同时连接多个后台进程时，每个 Socket 需要独立的解析状态。

6. **htons/ntohs 双重反转 Bug（调试中最隐蔽的字节序陷阱）**：

   **问题描述：** 协议帧中 LEN 字段为 2 字节大端序。在 ARM LE（小端）平台上，发送端使用 `htons(len)` 将主机字节序转为网络字节序（大端），然后提取字节时又用 `(len >> 8) & 0xFF` 和 `(len & 0xFF)` 拆分——在 ARM LE 上 `htons` 已经交换了高低字节，再次移位提取得到的是**双重反转**后的结果。例如原始长度 0x0014 (20)，htons→0x1400，`>>8` 得到 0x14（高字节），`&0xFF` 得到 0x00（低字节），拼回去变成了 0x1400 = 5120，完全错误。

   **现象：**
   - C→C 通信正常（发送 htons 双重反转 → 接收 ntohs 双重反转 → 恰好还原，两个错误互相抵消）
   - C→Qt 通信失败（C++ 端没有相应的反转逻辑）
   - Qt→C 通信失败（C++ 端发送时也没有反转，C 端 ntohs 收到原始值反而被反转了）
   - 表现为 av_daemon 问题 9（指令长度解析错误）和按键事件（key event）无响应

   **修复方案：** 直接按字节拆分和拼接，不使用 `htons`/`ntohs`。
   ```c
   // 错误写法（ARM LE 上双重反转）
   uint16_t net = htons(len);
   buf[0] = (net >> 8) & 0xFF;
   buf[1] = net & 0xFF;
   
   // 正确写法（直接字节拆分，与字节序无关）
   buf[0] = (len >> 8) & 0xFF;
   buf[1] = len & 0xFF;
   ```
   核心原理：协议帧中 LEN 的高字节永远在低地址（大端布局），直接在内存中按大端序写入即可，**不要再经过 htons 转换**。`htons` 的作用是"如果主机是小端就交换"，而手动按字节拆分本身就保证了字节顺序——两相结合反而错了。

   **教训：** 手动按字节拆分 = 已经完成了字节序控制；htons/ntohs 是给裸 `memcpy` + 网络传输用的。两者只能选其一，混用就会出双重反转 Bug。

### 1.6 unix_socket — UNIX Domain Socket 封装

**文件：** `src/common/socket/unix_socket.h`, `unix_socket.c`

**核心知识点：**

1. **AF_UNIX vs AF_INET**：API 完全一样，只改地址族。Linux "一切皆文件"哲学的体现——网络通信和本地通信用同一套 API。

2. **非阻塞 IO `fcntl(O_NONBLOCK)`**：`accept`/`recv`/`send` 在无数据时立即返回 -1（errno=EAGAIN），而非阻塞等待。这是 epoll 事件驱动的基础。

3. **`SO_REUSEADDR` 和 `unlink`**：服务端退出后残留 Socket 文件，下次 `bind` 会失败。启动时 `unlink` 删除旧文件。

4. **`send` 部分发送**：非阻塞 `send` 可能只发了部分数据就返回。循环发送直到全部完成。

5. **`MSG_NOSIGNAL`**：对端关闭连接时 `send` 不会发送 SIGPIPE 信号（该信号默认行为是终止进程），而是返回 EPIPE 错误码。

### 1.7 timer — 基于 timerfd 的软件定时器

**文件：** `src/common/timer/timer.h`, `timer.c`

**核心知识点：**

1. **timerfd 机制**：Linux 将定时器抽象为文件描述符，可以加入 epoll 统一监听。"一切皆 fd"的又一体现。

2. **`CLOCK_MONOTONIC` vs `CLOCK_REALTIME`**：单调时钟不受系统时间修改（NTP/手动）影响，适合周期性任务。墙上时钟受调整影响，适合闹钟类任务。

3. **必须 `read()`**：timerfd 使用"事件计数"机制。每次到期计数器 +1。如果不 `read` 清零，epoll 会一直触发——因为 fd 仍然可读。

4. **与 POSIX `timer_create` 冲突**：函数名重命名为 `timerfd_create_ms` 以避免与 POSIX 标准函数名冲突。

### 1.8 跨平台二进制协议对齐（调试中最重要的教训）

**问题：** C 和 C++ 之间通过二进制协议帧传递结构体，ARM 32 位上所有数据解析错误。

**根因：** `time_t` 在 ARM 32 位是 4 字节，C++ 端错写为 `uint64_t`（8 字节）。`#pragma pack(1)` 下：
- C 端 `dht11_data_t` = 4+4+1+4 = 13 字节
- C++ 端 `SensorData` = 4+4+1+8 = 17 字节
- daemon 发 13 字节，UI 按 17 字节解析 → 所有字段偏移错位

**教训：**
1. 跨语言二进制通信必须逐字段对比 sizeof
2. 使用 `static_assert(sizeof(CStruct) == sizeof(CppStruct))` 编译期验证
3. 优先使用固定宽度类型（`int32_t`）而非平台相关类型（`time_t`）
4. `#pragma pack(1)` 消除对齐填充，但不同平台的基础类型大小仍可能不同
5. **htons/ntohs 与手动字节拆分的互斥性**：手动按大端序拆分字节（`>> 8` / `& 0xFF`）后就不需要 `htons` 了——两者都是处理字节序的手段，混用会导致双重反转（详见 1.6 节）。同理，所有使用 `memcpy` 直接放入网络序字段的场景才需要 `htons`/`ntohs`。规则：**手动拆分 → 不用 htons，memcpy → 用 htons**。

## 第 2 章：guard_daemon — 系统守护进程

**文件：** `src/guard_daemon/`

**它做什么：** 所有进程的"父亲"——启动 5 个子进程、监控状态、崩溃自动重启。

**核心知识点：**

1. **双 fork 守护进程化 (daemonize)**：
   ```
   fork → 父进程exit → setsid(创建新会话) → fork → 父进程exit
   → chdir("/") → umask(0) → dup2(/dev/null, stdio)
   ```
   第二次 fork 确保进程不再是会话组长，永远无法重新获取终端。

2. **`fork + exec`**：`fork` 创建子进程（复制父进程地址空间），`exec` 替换为新程序。这是 Linux 创建新进程的标准方式。

3. **`SIGCHLD + waitpid(WNOHANG)`**：子进程退出时内核发送 SIGCHLD 给父进程。必须 `waitpid` 回收，否则子进程变成僵尸进程（占用进程表条目）。

4. **指数退避重启**：窗口内（60s）最多重启 5 次，超过则标记 ERROR 停止重试。防止崩溃→重启→崩溃的死循环。

5. **`/proc` 文件系统解析**：CPU 使用率（`/proc/stat`）、内存（`/proc/meminfo`）、负载（`/proc/loadavg`）、温度（`/sys/class/thermal/thermal_zone0/temp`）。

6. **`statfs`**：检查文件系统剩余空间，不足时告警并清理旧日志。

## 第 3 章：gps_daemon — GPS 定位进程

**文件：** `src/gps_daemon/`

**它做什么：** 通过串口读取 GPS 模块 NMEA-0183 数据，解析定位信息并计算里程。

**核心知识点：**

1. **termios 串口编程**：`cfmakeraw`（原始模式）+ `cfsetspeed`（波特率 9600）+ `CS8`（8 数据位）+ 非规范模式 `VMIN=0/VTIME=1`。

2. **NMEA-0183 字符级状态机**：不使用 `sscanf`。逐字符驱动状态转换：`IDLE→$→TALKER→TYPE→FIELD→*→CHECKSUM→CR→LF`。对格式错误（空字段、缺校验和）容错。

3. **NMEA 度分→十进制度**：`ddmm.mmmm → dd + mm.mmmm/60`。这是 GPS 数据处理的必备知识。

4. **Haversine 公式**：球面两点距离计算用于里程累计。里程过滤 1m 以下位移以避免 GPS 静止漂移。

5. **支持的 6 种 NMEA 语句**：
   - `$GPGGA` — GPS 定位数据（时间/经纬度/质量/卫星数/HDOP/海拔）
   - `$GPRMC` — 推荐最小定位信息（时间/经纬度/速度/日期）
   - `$GPGLL` — 地理定位信息（经纬度/时间/状态）
   - `$GPGSA` — 当前卫星信息（定位类型 2D/3D + DOP）
   - `$GPGSV` — 可见卫星状态信息
   - `$GPVTG` — 地面速度信息（km/h 直接获取）

## 第 4 章：Qt SensorThread — 温湿度监测

**文件：** `qt_ui/pages/sensor_thread.h`

**最终方案：** sensor_daemon 已删除。Qt SensorThread（独立 QThread）直接读 `/dev/mydht11`，signal 更新 UI。温湿度标签页通过 QTimer 定时刷新，线程每 2 秒读取一次传感器数据。

**核心知识点：**

1. **QThread 传感器读取**：继承 QThread，`run()` 中持续循环 `read(fd, buf, 2)`。`msleep(2000)` 仅在读到有效数据后调用，失败时立即重试——匹配 DHT11 驱动需持续轮询的特性。

2. **设备独占**：字符设备驱动通常只允许一个进程打开。原先 sensor_daemon 和 Qt 同时 open 导致双方都读不到数据。去掉独立进程后问题解决：只有一个进程打开设备。

3. **signal/slot 跨线程更新 UI**：QThread 中不能直接操作 UI 控件，需通过 signal 发射数据，主线程 slot 接收后更新 Label。emit 携带 `dht11_data_t` 结构体，包含温度、湿度、时间戳。

4. **错误处理**：文件不存在或打开失败时线程静默退出，UI 显示 "传感器未连接"，不会阻塞主界面。

## 第 5 章：input_daemon — 按键输入管理进程

**文件：** `src/input_daemon/`

**它做什么：** 监听 `/dev/input/event2`(gpio-keys) 的 KEY1/KEY2 物理按键，识别短按事件并通过 Socket 上报 Qt。Qt 根据当前活跃标签页分发按键功能。

**按键分发策略（Qt 端 Tab 分发）：**
| 当前标签页 | KEY1 功能 | KEY2 功能 |
|-----------|----------|----------|
| DVR 录像 | 拍照 | 暂停/继续 |
| 音乐播放 | 播放 | 暂停 |
| 其他标签 | 无操作 | 无操作 |

**核心知识点：**

1. **Linux input 子系统**：`/dev/input/eventX`，`struct input_event { timeval, type, code, value }`。`value=1` 按下，`0` 释放。设备树 `gpio-keys` 驱动。

2. **按键状态机（简化版）**：每按键独立状态机（IDLE→PRESSED→RELEASED），仅识别"按下→短时间释放"为有效短按。长按和双击均忽略，不做手势识别——简化设计后只保留最可靠的短按检测。

3. **`/dev/100ask_led` 字符设备 + 单次闪烁**：内核 LED 驱动，`write(fd, [idx, 0/1], 2)` 控制亮灭。按键触发时 LED 亮起 150ms 后自动熄灭（"闪一下"模式），不再是 press-on/release-off 的 toggle 模式。轮询循环中使用 `gettimeofday` 记录 LED 亮起时刻，每次 poll 返回后检查是否已过 150ms，到期则关闭 LED。

4. **poll 超时与 LED 超时的统一调度**：poll 超时不能设为固定值（LED 可能随时到期），需动态计算。若 LED 亮着，超时 = min(150ms - 已过时间, 正常超时)；若 LED 灭，超时 = 正常轮询间隔。以此实现单线程同时处理按键事件和 LED 定时。

5. **`/proc/bus/input/devices`**：查找按键设备对应 eventX 的方法。开机脚本中可自动检测并传入正确的设备路径。

## 第 6 章：canbus_daemon — CAN 总线通信进程

**文件：** `src/canbus_daemon/`

**它做什么：** 通过 SocketCAN 收发 CAN 报文，200 条环形缓冲实时监控。

**核心知识点：**

1. **SocketCAN (`PF_CAN`, `SOCK_RAW`, `CAN_RAW`)**：Linux 将 CAN 总线抽象为 Socket。API 与 TCP/UDP Socket 完全一样：`socket() → bind() → read()/write()`。

2. **CAN ID 位布局**：`can_id` 字段的 bit31=EFF_FLAG（扩展帧）、bit30=RTR_FLAG（远程帧）、bit29=ERR_FLAG（错误帧）。发送扩展帧时必须 `| CAN_EFF_FLAG`。

3. **CAN 错误帧**：内核自动生成。`data[6]=TEC`（发送错误计数）、`data[7]=REC`（接收错误计数）。总线状态：Error Active（<96）→ Error Passive（>127）→ Bus Off（>255）。

4. **`ioctl(SIOCGIFINDEX)`**：网络接口名（如 "can0"）→ 内核接口索引。Socket bind 需要的是索引号而不是名称。

---

## 第 7 章：av_daemon — 音频播放服务

**文件：** `src/av_daemon/`

**它做什么：** ALSA 播放 `/music/` 下的 WAV 文件，音量控制，播放列表循环。支持 Qt UI 触控 + 物理按键 KEY1/KEY2（音乐标签页时）。

**核心知识点：**

1. **ALSA PCM 同步播放**：`snd_pcm_open("hw:0,0")` → `snd_pcm_writei` 阻塞写入（和 `aplay -Dhw:0,0` 一致）。整文件读入内存，一次写入循环。

2. **WM8960 Mixer**：Speaker/Headphone 音量 + `Left/Right Output Mixer PCM` 开关（默认关闭需显式打开）。

3. **WAV RIFF 格式**：44 字节头解析采样率/声道/位深，数据起始偏移可能因额外 chunk 而非固定 44。

4. **播放中响应 Socket**：`snd_pcm_writei` 每次写入后用 `poll(..., 0)` 非阻塞检查 Socket 指令，实现播放中可暂停/停止。

5. **`_exit(0)` 退出**：信号处理器直接 `_exit(0)` 避免 `snd_pcm_close`/`pthread_join` 阻塞。

6. **物理按键控制（Tab 分发）**：当 Qt UI 当前选中"音乐"标签页时，KEY1 物理按键触发播放，KEY2 触发暂停。按键事件由 input_daemon 上报 Qt，Qt 根据活跃 Tab 转发指令给 av_daemon。

7. **文件方式传递辅助信息**：音量（`/tmp/av_volume`）和当前曲目名（`/tmp/av_track`）使用文件而非协议帧传递。原因是这些信息仅用于 UI 显示（非控制指令），使用简单文本文件避免了二进制协议解析的额外复杂度，且 Qt 端可随时读取最新值。二进制帧协议仅用于控制指令（播放/暂停/停止/音量调节）。

## 第 8 章：dvr_daemon — DVR 行车录像进程

**文件：** `src/dvr_daemon/`

**它做什么：** V4L2 采集 USB 摄像头画面，MJPEG 直存实现循环录像，支持暂停/继续和拍照。

**核心知识点：**

1. **V4L2 mmap 零拷贝采集**：这是整个项目中最复杂的 IO 操作。
   ```
   open → QUERYCAP → ENUM_FMT → S_FMT → REQBUFS(4)
   → QUERYBUF×4+mmap → QBUF×4 → STREAMON
   loop: DQBUF → [处理] → QBUF
   STREAMOFF → munmap → close
   ```
   mmap 将内核 DMA 缓冲区直接映射到用户空间，读帧时零拷贝。

2. **像素格式协商**：MJPEG 优先（硬件压缩，CPU 友好），不支持则回退 YUYV（原始数据需软件编码）。

3. **`ioctl` 万能接口**：Linux 设备驱动的控制接口。V4L2 有 20+ 种 ioctl 命令，从查询能力到设置格式到控制缓冲区队列。

4. **暂停/继续录像机制**：暂停时停止写入文件但保持 V4L2 采集（防止缓冲区溢出），恢复时 `open_segment` 创建新分段文件继续写入。总录制时长仅在写入时累积——暂停期间时钟暂停，恢复后新分段追加到总时长。此机制保证每段文件内容连续，不会在文件中插入暂停期间无效帧。

5. **录像文件管理**：文件保存到 `/record/` 目录（非 `/tmp/`，避免内存文件系统空间不足）。按时间分段（60s/段），按容量管理（超限自动删最老）。`stat` 遍历目录获取文件大小和修改时间。

6. **拍照功能**：MJPEG 帧已经是 JPEG 数据，直接 `fwrite` 存为 `.jpg` 文件，零转码开销。照片保存到 `/record/photo_0001.jpg`，自动递增编号。

7. **物理按键控制（Tab 分发）**：当 Qt UI 当前选中"DVR"标签页时，KEY1 物理按键触发拍照，KEY2 触发暂停/继续。按键事件由 input_daemon → Qt Socket → Qt Tab 分发 → dvr_daemon Socket 指令 → 执行。

8. **Qt UI 录制时长显示**：dv_daemon 通过 Socket 周期性发送当前录制时长。Qt DVR 标签页显示已录制时间（HH:MM:SS 格式），录制中红色闪烁提示，暂停时橙色显示。

9. **调试中踩过的坑：**
   - **memset/路径别名 Bug**：`dvr_storage_init` 中 `path` 变量与 `st->base_path` 指向同一块内存（`snprintf` 构造路径后直接赋值），导致后续 `memset(st, 0, sizeof(...))` 时将 base_path 清零，录制目录变为空字符串。修复：使用独立局部缓冲区构造路径后再 `strncpy`。
   - **open_segment 缺少 mkdir**：`fopen("/record/seg_xxx.mjpg", "w")` 前未检查目录是否存在。首次启动时 `/record/` 可能不存在，导致 fopen 静默失败，磁盘上无任何录像文件。修复：`fopen` 前先 `mkdir("/record/", 0755)`（已存在则忽略 EEXIST）。

## 第 9 章：net_daemon — 网络服务进程（已删除/未激活）

**文件：** `src/net_daemon/`（源码保留但未编译运行）

**状态说明：** 当前项目版本不启动该进程。代码保留作为学习参考（非阻塞 TCP、HTTP 客户端、JSON 解析等技术点仍有价值），但 guard_daemon 的启动列表和 Makefile 中均已移除。当前系统仅通过 Qt UI 的简化 HTTP 请求获取天气信息（Qt 内置 `QNetworkAccessManager`），不再需要独立后台进程。

**原始设计（仅供学习参考）：**

1. **非阻塞 TCP connect**：`connect() → EINPROGRESS → epoll EPOLLOUT → getsockopt(SO_ERROR)`。非阻塞 connect 让进程可以同时做其他事。

2. **手动 HTTP/1.1 客户端**：不使用 curl。`snprintf` 构造请求行+头部，逐行解析响应（状态行→头部→`\r\n\r\n`→正文）。Content-Length 确定正文长度。

3. **最小化 JSON 解析器**：不使用第三方库。字符串搜索 `"key":` → `strtod/strtol` 提取值。支持嵌套对象的浅层查找。

4. **指数退避重连**：`delay = min(initial × multiplier^attempt, max)`。1s→2s→4s→8s→...→60s。避免网络恢复时所有客户端同时重连造成拥塞。

5. **`/sys/class/net/` 网络监控**：`operstate`（管理状态 up/down）、`carrier`（物理链路 0/1）。优先级：以太网 > WiFi > 4G。

6. **`getaddrinfo`**：现代的 DNS 解析函数，替代过时的 `gethostbyname`。支持 IPv4/IPv6 过滤。

## 第 10 章：qt_ui — Qt 触控界面

**文件：** `qt_ui/`

**它做什么：** 5 个标签页（仪表盘/DVR/音乐/CAN/温湿度），5 路 QLocalSocket 连接 5 个后台进程。作为整个系统的"调度中心"，负责 UI 渲染、Socket 事件分发、物理按键按 Tab 路由。

**标签页布局（最终版）：**

| 标签页 | 功能 |
|--------|------|
| 仪表盘 | 系统状态总览（CPU/内存/温度/GPS 定位） |
| DVR | 摄像头预览 + 录制控制 + 录制时长 |
| 音乐 | 播放列表 + 音量 + 曲目信息 |
| CAN | CAN 报文收发 + 实时监控 |
| 温湿度 | 温度/湿度实时显示 |

已移除标签页：按键调试页（input device tab）、设置页——物理按键功能已整合到 Tab 分发逻辑中，不再需要独立调试页面。

**Socket 连接架构（5 路 QLocalSocket）：**

| 连接名称 | 目标进程 | 用途 |
|---------|---------|------|
| guard | guard_daemon | 系统状态/CPU/内存 |
| gps | gps_daemon | 定位数据 |
| input | input_daemon | 按键事件接收 |
| av | av_daemon | 音乐控制指令 |
| dvr | dvr_daemon | 录像控制 + 状态 |
| canbus | canbus_daemon | CAN 报文收发 |

每个 `QLocalSocket` 有独立的 `ProtocolParser`（C 库桥接），按 1.6 节协议帧格式解析/封装。非阻塞 + `readyRead` 信号驱动。

**核心知识点：**

1. **Qt Designer `.ui` 文件**：`FORMS += mainwindow.ui`，`ui->setupUi(this)` 自动生成布局代码。比手写 QWidget 代码更直观，适合嵌入式触控界面快速开发。

2. **Qt linuxfb + tslib 触控**：`QT_QPA_PLATFORM=linuxfb:fb=/dev/fb0` 直接写 framebuffer，`QT_QPA_GENERIC_PLUGINS=tslib:/dev/input/event1` 驱动触摸屏。

3. **C/C++ 二进制协议对齐陷阱**：ARM 32 位 `time_t` = 4 字节 ≠ x86 `uint64_t`。跨语言通信必须确保 `#pragma pack(1)` 下结构体逐字节一致。`static_assert(sizeof(...))` 编译期验证是最佳实践。详见 1.9 节的 htons/ntohs 和 time_t 双重教训。

4. **DVR 预览折中方案**：UNIX Socket 传输 MJPEG 帧太慢（30~50KB/帧），改用 dvr_daemon 周期性写固定路径 `/tmp/dvr_preview.jpg`，Qt QTimer 每秒加载 QPixmap 显示。牺牲实时性换可行性。

5. **QLocalSocket 自动重连**：断线后 `QTimer` 每秒重试，`setObjectName` 标识客户端以便按名称查找发送指令。

6. **物理按键 Tab 分发**：从 input_daemon 收到按键事件后，根据 `ui->tabWidget->currentIndex()` 判断当前活跃标签页，按 5.2 节表格路由 KEY1/KEY2 到对应功能。分发逻辑在 `mainwindow.cpp` 的 `onKeyEvent` slot 中实现。

7. **DVR 录制时长显示与状态机**：QTimer 每秒 `++duration_seconds` 累加录制时长，格式化 HH:MM:SS 显示。按钮状态机 `btn_state`（0=IDLE, 1=RECORDING, 2=PAUSED）控制按钮文字和颜色：IDLE 显示"开始录像"（灰），RECORDING 显示"暂停"（红色闪烁），PAUSED 显示"继续"（橙色）。

8. **CAN 发送报文填充**：发送缓冲区扩展为完整 `can_msg_t`（15 字节），包含 CAN ID（4B）、DLC（1B）、Data（8B）、Flags（1B）、Timestamp（1B）。Qt UI 构造报文后直接通过 Socket 发送给 canbus_daemon，daemon 端负责 SocketCAN 写入。

9. **线程模型**：Qt 主线程处理 UI 事件 + Socket IO，SensorThread（QThread）单独处理 `/dev/mydht11` 读取。所有 daemon Socket 的 `readyRead` 通过事件循环在主线程中处理，无需额外线程。

## 附录 B：IPC 通信协议帧格式

```
[0xAA][0x55][TYPE][LEN_H][LEN_L][DATA...][CRC8][0x55]
   2B     1B     2B(大端)   0~65535B    1B    1B
总开销: 7 字节
```

- 帧头 0xAA55：双字节互补序列，随机数据中极少出现
- LEN 大端序：网络字节序标准。**注意：实现中直接按字节拆分 `(len >> 8) & 0xFF`, `len & 0xFF`，不使用 htons。** 原因见 1.6 节 htons/ntohs 双重反转 Bug——手动字节拆分与 htons 功能重叠，混用导致 ARM LE 上双重反转。
- CRC8 多项式 0x07：覆盖 TYPE+LEN+DATA，不包括固定帧头帧尾
- 消息类型高 4 位=模块 ID，低 4 位=消息 ID

## 附录 E：调试中遇到的典型 Bug 模式

实际开发中遇到的、教科书上不常见但嵌入式/跨语言项目中高频出现的 Bug 模式。

### E.1 memset/路径别名陷阱（dvr_daemon）

**现象：** 录制文件路径丢失，文件保存到空目录。

**根因：** 局部变量 `path` 直接赋值为 `st->base_path` 指针（而非拷贝内容），之后 `memset(st, 0, sizeof(...))` 清零结构体时把 base_path 也清零了——而 `path` 指向的正是同一块内存。

**教训：** `memset` 前检查是否有别名指向同一块内存。路径/字符串赋值使用 `snprintf` 构造到独立缓冲区后再 `strncpy`，避免指针别名。

### E.2 htons 双重反转陷阱（protocol）

**现象：** C→C 通信正常，C→Qt 和 Qt→C 均失败。

**根因：** ARM LE 上 `htons()` 交换字节 → 手动 `>> 8` / `& 0xFF` 再次按字节拆分 → 双重反转。C→C 时两端都用 htons+手动拆分，两次反转恰好抵消；跨语言时 Qt 端没有对应的反转逻辑，暴露问题。

**教训：** 手动按字节拆分 **等于** 已完成字节序控制。规则：手动拆分 → 不用 htons/ntohs；裸 memcpy → 用 htons/ntohs。两者二选一，不可混用。

### E.3 栈垃圾 / 未初始化协议缓冲区（av_daemon）

**现象：** 协议帧中 DATA 字段偶尔包含随机垃圾数据，CRC 校验偶尔失败。

**根因：** 栈上声明的 `uint8_t buf[MAX_FRAME]` 未初始化（`= {0}`），发送时 `send()` 使用了声明长度而非实际填充长度，导致帧尾包含栈上的随机数据。

**教训：** 栈缓冲区使用前必须 `memset` 清零或声明时 `= {0}`。协议帧发送时以实际填充长度为准，不能粗暴地用 `sizeof(buf)` 或 `MAX_FRAME`。

### E.4 设备独占竞争（sensor）

**现象：** sensor_daemon 和 Qt SensorThread 同时运行，双方都读不到 `/dev/mydht11` 数据。

**根因：** 字符设备驱动通常只允许一个进程 open。两个进程同时 open 会导致竞争，驱动行为不确定。

**教训：** 同一字符设备只由一个进程打开。多消费者场景下考虑通过 Socket 中转数据，而非多进程直接 open 同一设备。
