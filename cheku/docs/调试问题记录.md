### 问题 1：`localtime_r` 隐式声明

**报错信息：**
```
log/log.c:143:5: warning: implicit declaration of function 'localtime_r'
```

**原因：** `common/Makefile` 使用了 `-std=c99`，严格 C99 标准禁用了 POSIX 扩展函数（`localtime_r` 是 POSIX 标准函数，不在 C99 中）。

**解决方法：** `src/common/Makefile` 第 35 行

```diff
- CFLAGS  = -Wall -Wextra -std=c99 -Os -g -fPIC
+ CFLAGS  = -Wall -Wextra -std=gnu99 -Os -g -fPIC
```

`gnu99` = C99 + GNU 扩展 + POSIX 函数。

---

### 问题 2：`LOG_BUF_SIZE` 未声明

**报错信息：**
```
log/log.c:314:21: error: 'LOG_BUF_SIZE' undeclared
```

**原因：** `log.c` 只 include 了 `log.h`，但 `LOG_BUF_SIZE` 宏定义在 `common.h` 中。

**解决方法：** `src/common/log/log.c` 在 `#include "log.h"` 之后添加：

```c
#include "../common.h"       /* LOG_BUF_SIZE, ret_code_t, 公共类型 */
```

### 问题 3：`size_t` 未知类型

**报错信息：**
```
config/config.h:128:60: error: unknown type name 'size_t'
```

**原因：** `config.h` 只 include 了 `<stdint.h>`，但 `size_t` 定义在 `<stddef.h>` 中。使用 `-std=gnu99` 后头文件不再隐式包含 `<stddef.h>`。

**解决方法：** `include/config/config.h` 添加：

```c
#include <stddef.h>    /* size_t */
```

---

### 问题 4：`ringbuffer_t` 类型冲突

**报错信息：**
```
ringbuffer/ringbuffer.h:56:3: error: conflicting types for 'ringbuffer_t'
protocol/protocol.h:61:29: note: previous declaration of 'ringbuffer_t' was here
```

**原因：** `protocol.h` 前向声明 `typedef struct ringbuffer_t ringbuffer_t;`（带 tag 名），但 `ringbuffer.h` 实际定义是匿名 struct：`typedef struct { ... } ringbuffer_t;`。C 语言中匿名 struct 和带 tag 名的 struct 是不同类型。

**解决方法：**

① `include/ringbuffer/ringbuffer.h`：给 struct 加 tag 名
```diff
- typedef struct {
+ typedef struct ringbuffer {
      ...
  } ringbuffer_t;
```

② `include/protocol/protocol.h`：删除前向声明，直接 include 完整头文件
```diff
- /* 前置声明 */
- typedef struct ringbuffer_t ringbuffer_t;
+ #include "../ringbuffer/ringbuffer.h"
```

③ `src/common/protocol/protocol.c`：删除重复的 include
```diff
- #include "../ringbuffer/ringbuffer.h"
```

---

### 问题 5：`timer_create` 与 POSIX 函数冲突

**报错信息：**
```
time.h:240:12: error: conflicting types for 'timer_create'
timer/timer.h:70:5: note: previous declaration of 'timer_create' was here
```

**原因：** POSIX 标准已有 `timer_create(clockid_t, struct sigevent*, ...)` 函数。我们自定义的 `timer_create(uint32_t)` 签名不同，产生冲突。`<sys/timerfd.h>` → `<time.h>` 引入了 POSIX 声明。

**解决方法：** 全局重命名 `timer_create` → `timerfd_create_ms`

涉及文件：
- `include/timer/timer.h` — 声明
- `src/common/timer/timer.c` — 定义
- 所有 daemon `.c` 中的调用点（9 个文件）

```bash
sed -i 's/timer_create(/timerfd_create_ms(/g' src/**/*.c
```

---

### 问题 6：`common.h` 找不到

**报错信息：**
```
gps_daemon.h:33:10: fatal error: common.h: No such file or directory
```

**原因：** daemon Makefile 的 include 路径 `-I$(COMMON_INC)` 指向 `src/`，但 `common.h` 位于 `src/common/`，不是 `src/`。

**解决方法：** 所有 daemon 的 Makefile 添加子目录路径：

```diff
- CFLAGS += -I$(COMMON_INC)
+ CFLAGS += -I$(COMMON_INC) -I$(COMMON_INC)/common
```

---


### 问题 8：`protocol_parser_t` 和 `ringbuffer_t` 类型未知

**报错信息：**
```
gps_daemon.h:133:5: error: unknown type name 'protocol_parser_t'
gps_daemon.h:134:5: error: unknown type name 'ringbuffer_t'
warning: passing argument 1 of 'ringbuffer_init' from incompatible pointer type
```

**原因：** `gps_daemon.h` 的 `gps_context_t` 结构体中嵌入了 `ringbuffer_t` 和 `protocol_parser_t` 实例（非指针），需要完整的类型定义而不仅仅是前向声明。但 `common.h` 不能 include `protocol.h`（会造成循环依赖）。

**解决方法：**

① `include/protocol/protocol.h`：给 `protocol_parser_t` 的 struct 加 tag
```diff
- typedef struct {
+ typedef struct protocol_parser {
```

② `include/common.h`：添加前向声明（供指针使用）
```c
struct ringbuffer;      typedef struct ringbuffer ringbuffer_t;
struct protocol_parser; typedef struct protocol_parser protocol_parser_t;
```

③ 所有需要嵌入实例的 daemon `.h` 文件添加完整 include：
```c
#include "protocol/protocol.h"   /* ringbuffer_t, protocol_parser_t */
```

涉及 6 个 daemon header：`gps_daemon.h`, `canbus_daemon.h`, `av_daemon.h`, `dvr_daemon.h`, `net_daemon.h`, `guard_daemon.h`

## sensor_daemon 模块（2026-08-08）

### 硬件环境

- 开发板已安装 DHT11 内核驱动，设备路径 `/dev/mydht11`
- 驱动接口：`open(O_RDWR | O_NONBLOCK)` → `read(fd, buf, 2)` → `buf[0]=湿度, buf[1]=温度`

---


### 问题 1：`errno=EIO` — DHT11 驱动读取偶发失败

**现象：**
```
[WARN] read failed: n=-1, errno=5 (Input/output error)
```

**原因：** DHT11 传感器偶发读失败（时序抖动/校验失败）时，内核驱动返回 `EIO` 而非 `EAGAIN`。用户的测试程序静默跳过（只判断 `== 2`，不检查错误码）。

**解决方法：** 在 `dht11_read()` 中将 `EIO` 与 `EAGAIN` 同等对待，静默跳过等下次采样：

```c
if (n == -1 && (errno == EAGAIN || errno == EWOULDBLOCK || errno == EIO))
    return -1;  // 静默跳过
```

---

### 问题 2：`epoll_wait` 卡死 — timerfd/signalfd 不触发（排查耗时最长）

**现象：** 程序启动后打印 "Event loop started." 后完全无输出，Ctrl+C 也无响应。

**排查过程：**

| 尝试 | 方法 | 结果 |
|------|------|------|
| 1 | `epoll` + `timerfd` + `signalfd` | ❌ epoll_wait 永久阻塞 |
| 2 | DHT11 fd 加入 epoll（事件驱动读取） | ❌ 驱动不支持 `.poll`，epoll 行为异常 |
| 3 | 移除 DHT11 fd，仅 timerfd + signalfd | ❌ 仍然阻塞 |
| 4 | `epoll_wait` 超时从 -1 改为 2000ms | ❌ 超时不生效 |
| 5 | 换用 `poll()` 替代 `epoll` | ✅ poll 正常返回 |
| 6 | `poll()` + 短时间重试读取 DHT11 | ✅ 成功运行 |

**根因：** 开发板内核 (Linux 4.9.88) 的 `timerfd` / `signalfd` / `epoll` 与某些配置组合存在兼容性问题。`poll()` 是 POSIX 标准接口，兼容性最好。

**最终方案：** 使用 `poll()` + `signal()` 替代 `epoll` + `timerfd` + `signalfd`。

---

### 问题 3：DHT11 驱动单次 `read()` 耗时 ~230ms

**现象：** 计时诊断显示单次 `read(fd, buf, 2)` 耗时 227~243ms。

```log
[DEBUG] [dht11] read OK: T=28 H=54 cost=235ms
```

**原因：** DHT11 内核驱动内部进行传感器读取时序（起始信号→等待响应→读取 40bit），即使应用层开了 `O_NONBLOCK`，驱动内部仍需要 ~230ms 完成一次硬件交互。

**影响：** 主线程调用 `dht11_read()` 时会阻塞 ~230ms。如果加入重试循环（5 次 × 50ms 间隔），最坏情况阻塞 1400ms+。

---

### 问题 4：重试循环拖慢采样周期

**现象：** 配置 2000ms 采样间隔，实际周期 2~3.5 秒不等。

```log
sample cost=227ms  tries=0  → 周期 ~2.2s  ✓
sample cost=1092ms tries=3  → 周期 ~3.1s  ⚠
sample cost=1418ms tries=5  → 周期 ~3.4s  ✗ (全部失败)
```

**原因：** 采样在主线程同步执行，重试耗时直接累加到 poll 超时上：`总周期 = poll(2000ms) + sample_cost(227~1400ms)`。

**解决方法：** 限制重试 5 次 × 50ms = 250ms 上限。失败直接丢弃等下一周期。实际上 5 次重试 50ms 间隔 ≈ 250ms + 驱动 230ms ≈ 480ms 最坏情况，周期抖动控制在 2.5s 以内。

---


### 运行测试结果

成功运行输出（每 2~3 秒一条，滤波平滑):

```
[INFO] T=28.0℃(raw:28.0) H=54.0%(raw:54.0)
[INFO] T=28.0℃(raw:28.0) H=56.8%(raw:56.0)
[INFO] T=28.0℃(raw:28.0) H=58.2%(raw:64.0)
```

- DHT11 读取正常、滤波有效、Socket 创建正常
- Ctrl+C 资源全部正确释放

## input_daemon 模块（2026-08-08）

### 硬件环境

- 设备树 `gpio-keys`: KEY1→`KEY_1`(code=2, gpio5-1), KEY2→`KEY_2`(code=3, gpio4-14)
- LED 驱动: `/dev/100ask_led` 字符设备

---

### 问题 1：epoll/timerfd → poll 模式转换

**现象：** 使用旧 epoll+timerfd 架构时按键无反应。

**解决：** 改为 `poll([input_fd, server_fd, client_fd], 50ms)`，利用 poll 超时驱动 key_parser 状态机 tick。

---

### 问题 2：LED 控制从 sysfs 改为 `/dev/100ask_led`

**原因：** 开发板有内核 LED 驱动 (`led_drv.c`)，接口为 `write(fd, [led_index, value], 2)`。

**解决：** 重写 `led_control.c`，API 改为 `led_init()`/`led_on(which)`/`led_off(which)`。删除 sysfs trigger/brightness 操作。

---

### 问题 3：按键码映射错误

**现象：** daemon 用 `KEY_F1`/`KEY_F2` 映射，设备树实际用 `KEY_1`(code=2)/`KEY_2`(code=3)。

**解决：** `g_default_key_map` 改为 `{ KEY_1, KEY_ID_KEY1 }` / `{ KEY_2, KEY_ID_KEY2 }`。

---

### 问题 4：按键设备用错 eventX

**现象：** daemon 默认 `event0`，但 `/proc/bus/input/devices` 显示 gpio-keys 在 `event2`。

**解决：** `config.ini` 和 `INPUT_DEFAULT_DEVICE` 改为 `/dev/input/event2`。

---

### 测试结果

```bash
./input_daemon /dev/input/event2
# 按 KEY1 → [INFO] Key1 SHORT + LED0 闪烁一次 (亮150ms后自动熄灭)
# 按 KEY2 → [INFO] Key2 SHORT + LED0 闪烁一次
```

---

### 问题 5：LED 改为闪烁一次 + 按键功能分发 (2026-08-11)

**需求：** KEY1/KEY2 根据 Qt UI 当前标签页执行不同功能：
| 标签页 | KEY1 | KEY2 |
|--------|------|------|
| DVR | 📷 拍照 | ⏯ 暂停/继续录像 |
| 音乐 | ▶ 播放 | ⏸ 暂停 |
| 其他 | 仅显示按键信息 | 仅显示按键信息 |

LED 每次短按闪烁一次（亮 150ms → 自动熄灭），不再 toggle。

**实现：**

① `input_daemon.c` — LED 从 toggle 改为 blink-once：
- 短按事件触发 `led_on(0)` + 记录 `led_on_time`
- poll 循环中检查：超过 `LED_BLINK_MS(150ms)` → `led_off(0)`
- 长按/双击不触发 LED（避免多次闪烁）

② `mainwindow.cpp` — 按键按 Tab 分发：
- `MSG_KEY_EVENT` 处理中检查 `ui->tabWidget->currentIndex()`
- Tab 1 (DVR): `key_id==1` → `MSG_DVR_SNAPSHOT`, `key_id==2` → `MSG_DVR_PAUSE`
- Tab 2 (音乐): `key_id==1` → `MSG_AV_PLAY`, `key_id==2` → `MSG_AV_PAUSE`
- 仅 `event_type==1` (短按) 触发功能，长按/双击忽略

## canbus_daemon 模块（2026-08-08）

### 问题 1：`SOL_CAN_RAW` / `CAN_RAW_ERR_FILTER` 未定义

**现象：**
```
can_driver.c:146:24: error: 'SOL_CAN_RAW' undeclared
can_driver.c:146:37: error: 'CAN_RAW_ERR_FILTER' undeclared
```

**原因：** 内核 4.9.88 的 `<linux/can/raw.h>` 头文件未导出这两个常量。

**解决：** `can_driver.c` 手动定义：

```c
#ifndef SOL_CAN_RAW

#endif

#endif
```

### 问题 2：`uint8_t > 255` 无效比较

**现象：** `warning: comparison is always false due to limited range of data type`

**原因：** `tec`/`rec` 是 `uint8_t` 类型（最大值 255），`> 255` 永远为 false。

**解决：** 删除 `> 255` 检查，仅保留 `> 127`（Error Passive 阈值）。

---

### 问题 3：未使用变量

**现象：** `unused variable 'n'` / `unused variable 'frame'` in `handle_can_event`

**解决：** 删除未使用的局部变量。

---

### 问题 4：CAN 接口 DOWN 状态

**现象：** 首次运行日志输出 `CAN interface is DOWN`，`ip -d link show can0` 显示 `state STOPPED`。

**原因：** 开发板 CAN 接口默认未配置，需要手动启用。

**解决：** 使用以下命令配置并启用 loopback 模式（无外部 CAN 设备时测试用）：

```bash
# 关闭 can0
ip link set can0 down

# 配置 500K 波特率 + loopback 回环模式 + 自动恢复

# 启用
ip link set can0 up

# 验证状态
ip -d link show can0
# 期望看到: <LOOPBACK> state ERROR-ACTIVE
```

启用后重启 `./canbus_daemon`，不再出现 DOWN 警告，状态定时上报正常。

## av_daemon 模块（2026-08-08）

### 硬件环境

- WM8960 codec (I2C2 addr 0x1a), SAI2, 12.288MHz MCLK
- 喇叭/耳机双输出

---

### 问题 1：epoll/timerfd → poll 模式切换

**现象：** `Event loop started.` 后 `feed_alsa` 从未执行，无声音。

**原因：** 与 sensor/dvr 相同，epoll/timerfd 在开发板上不工作。

**解决：** 改为 `poll([decoder_pipe, server_fd, client_fd], 100ms)`，超时触发 `feed_alsa`。

---

### 问题 2：WM8960 PCM 输出通路默认关闭 → 无声音

**现象：** ALSA 打开成功、音量设置成功、WAV 解析正常、数据喂入正常，但喇叭/耳机无声音。

**排查：** `audio_mixer_list_controls()` 列出全部 48 个 mixer 控制，发现 `Left Output Mixer PCM` 和 `Right Output Mixer PCM` 是开关（非音量）。

**根因：** 这两个开关控制 PCM 音频流到输出放大器通路，WM8960 驱动默认关闭！

**解决：** 新增 `audio_mixer_set_switch()` 函数，启动时显式打开：
```c
audio_mixer_set_switch(g_mixer, "Left Output Mixer PCM", 1);
audio_mixer_set_switch(g_mixer, "Right Output Mixer PCM", 1);
```

---

### 问题 3：`Ext Spk` mixer 元素不存在

**现象：** 设备树 `audio-routing` 使用 `"Ext Spk"` 标签，尝试设置该元素时报 `not found`。

**原因：** 设备树路由标签 ≠ ALSA mixer 元素名。WM8960 驱动的实际元素名为 `"Speaker"`。

**解决：** 使用 `"Speaker"` / `"Headphone"` 元素名。

---

### 问题 4：播放无声音 — 设备改用 hw:0,0

**现象：** `aplay -Dhw:0,0 jatchou.wav` 可播放，daemon 默认用 `"default"` 设备无声音。

**解决：** PCM 设备改为 `"hw:0,0"`（card 0: wm8960audio, device 0: HiFi）。

### 问题 5：分块写入 + 位置追踪导致文件疯狂重读

**现象：** `snd_pcm_writei` 返回错误时 `fread` 已前进文件位置，`g_pos` 未更新，数据丢失→重读→死循环。

**解决：** 改为整文件一次性读入内存 + 阻塞 `snd_pcm_writei` 循环（和 aplay 一致）。写失败时 `fseek` 回退。

### 问题 6：退出时终端卡死

**解决：** 信号处理器用 `_exit(0)` 直接退出，不做 cleanup。

### 问题 7：音量太小

**解决：** 默认音量从 70 调到 100%。

### 问题 8：C++ CRC 分段计算 bug → 协议帧校验和错误

**现象：** Qt 发 PLAY/PAUSE 正常，VOLUME 帧 daemon 收不到。

**根因：** C++ `crc8()` 不支持初始值参数。`pack()` 中两次调用 `crc8()`，第二次从 0x00 开始，覆盖第一次结果。对空数据帧 (PLAY/PAUSE) 恰好 CRC=0x00 能过，有数据帧 (VOLUME) CRC 错。

**解决：** 删除 CRC 校验（C/C++ 两端均不再计算/验证 CRC）。

### 问题 9：8 字节协议帧解析失败 → 根因定位：htons/ntohs 双字节序反转 (2026-08-11 定位)

**现象：** 删除 CRC 后 VOLUME 帧 (8 字节) 仍无法解析，PLAY/PAUSE (7 字节) 正常。

**根因定位（之前未找到）：** `protocol_pack` 和 `protocol_unpack` 中 `htons`/`ntohs` 的使用方式错误。

`protocol_pack` 编码长度时：
```c
net_len = htons((uint16_t)data_len);  // ARM LE: htons(10) → 0x0A00
frame[LEN_H] = (net_len >> 8) & 0xFF;  // = 0x0A  ← 错!
frame[LEN_L] = net_len & 0xFF;         // = 0x00  ← 错!
// 帧中存的是 [0x0A][0x00] = 2560, 而非 [0x00][0x0A] = 10!
```

`htons` 返回值的**内部表示**在小端序机器上已交换了字节，再用 `>> 8` 和 `& 0xFF` 取高低字节等于把交换又还原了，结果高低字节反了。

`protocol_unpack` 解码时用了 `ntohs`：
```c
data_len = ntohs((header[1] << 8) | header[2]);
// 帧中是 [0x0A][0x00], 构造值 = 0x0A00
// ARM LE: ntohs(0x0A00) = 0x000A = 10 ✓ (两个错误抵消!)
```

**C→C 通信碰巧正常**（htons 编码错 + ntohs 解码错 = 负负得正），但 **C→Qt / Qt→C 全坏**。Qt 端直接 `(byte[1]<<8)|byte[2]` 不做 ntohs 反转，读到的是错误的大数值。

这解释了所有现象：
| 消息方向 | 数据长度 | htons错+ntohs反 | 结果 |
|---------|---------|-----------------|------|
| Qt→Daemon | 0 (START/STOP/PLAY) | htons(0)=0, 不受影响 | ✅ |
| Qt→Daemon | >0 (VOLUME/CAN_SEND) | Qt pack无htons → 帧正确, C unpack有ntohs → 解码错 | ❌ |
| Daemon→Qt | 0 (ACK) | 不受影响 | ✅ |
| Daemon→Qt | >0 (GPS/状态/按键) | C pack有htons → 帧错, Qt unpack无ntohs → 读到错误长度 | ❌ |

**解决：** `protocol_pack` 直接拆分原始值的高低字节（不用 htons），`protocol_unpack` 直接拼接（不用 ntohs）：

```c
// pack: 直接拆分
frame[LEN_H] = (uint8_t)((data_len >> 8) & 0xFF);
frame[LEN_L] = (uint8_t)(data_len & 0xFF);

// unpack: 直接拼接
data_len = ((uint16_t)header[1] << 8) | (uint16_t)header[2];
```

**教训：** 当手动拆分/拼接字节时，不要再用 htons/ntohs，否则在小端序平台上会做两次字节反转。

### 问题 10：WM8960 音量非线性 — 50% 即无声

**现象：** 滑块调到一半就彻底没声音。

**根因：** WM8960 的 raw 值 0-127 与感知音量不是线性关系。50% → raw=63 已经非常小。

**解决：** 映射改为 `raw = 滑块==0 ? 0 : 40 + 滑块*87/100`。0%=静音，1%=raw40(可听)，100%=raw127(最大)。

### 问题 11：协议过度设计

**教训：** 同一板子上的 UNIX Socket 通信，二进制帧协议（帧头/长度/CRC/帧尾/状态机解析）是过度设计。简单文本协议（`PLAY\n`、`VOL 70\n`）更可靠、更易调试。

### 问题 4：录像无文件保存 — `dvr_storage_init` 的 memset 清零经典 bug

**现象：** 拍照正常保存到 `/record/`，但录像点击开始后无任何文件产生。日志显示：

```
Segment #1: /19700101_030005_dvr.h264          ← 路径前缀 /record/ 丢失！
Snapshot saved: /record//19700101_030001_002.jpg ← 拍照路径正常
```

视频文件被写到根目录 `/`（权限不足，静默失败）。

**根因：** `main()` 中的调用：
```c
dvr_storage_init(&g_ctx.storage, g_ctx.storage.base_path, ...);
//               ^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^^^^^^^^^^^
//                st 指针           path 指向 st->base_path（同一块内存!）
```

`dvr_storage_init` 内部先 `memset(st, 0, sizeof(*st))` 把 `base_path` 清零，然后 `strncpy(st->base_path, path, ...)` 从 `path` 拷贝——但 `path == st->base_path`，源和目标相同，拷贝的是已被清零的空字符串。

拍照没受影响是因为 `save_snapshot` 有空字符串 fallback：`base_path[0] ? base_path : "/record/"`。

**解决：** `storage_mgr.c` 中在 `memset` 之前用局部变量保存 path：

```c
char saved_path[256];
strncpy(saved_path, path, sizeof(saved_path) - 1);
memset(st, 0, sizeof(*st));           // ← 现在清零不影响 saved_path
strncpy(st->base_path, saved_path, ...); // ← 从局部变量恢复
```

修复后日志：
```
Segment #1: /record/19700101_030005_dvr.h264    ← 路径正确!
```

**教训：** 当函数参数指针可能指向结构体内部成员时，`memset` 清零结构体前必须保存参数值。

### 问题 4：C/C++ 结构体大小不一致 — 数据解析全部错位

**现象：** UI 连接后台成功但温湿度/按键/GPS 速度全部不显示。

**根因：** ARM 32 位 `time_t` = 4 字节，但 Qt C++ 端的 `SensorData.timestamp` 和 `KeyEvent.timestamp` 写成了 `uint64_t`（8 字节）。`#pragma pack(1)` 下：
- C 端 `dht11_data_t` = 13 字节
- C++ 端 `SensorData` = 17 字节

`sock_send_frame` 发送 13 字节，UI 按 17 字节解析，所有字段偏移都错位。

**解决：** `protocol_handler.h` 中 `uint64_t timestamp` → `uint32_t timestamp`。

**教训：** 跨语言/跨平台二进制通信，必须确保结构体逐字节一致。最佳实践：用 `static_assert(sizeof(...))` 编译期验证。
