# 智能车载终端 — 项目简历

## 项目概述

基于 **NXP i.MX6ULL** (ARM Cortex-A7 528MHz / 512MB DDR3 / 4GB eMMC) 开发板，从零搭建了一套完整的**智能车载终端系统**。包含 5 个后台 C 语言守护进程 + 1 个 Qt 触控界面，通过 UNIX Socket IPC 通信，LCD 1024x600 触控交互。

**代码规模：** ~15,000 行 C/C++，85+ 源文件，全部手写，doxygen 注释覆盖。

---

## 核心技术栈

| 类别 | 技术 |
|------|------|
| 语言 | C (C99/gnu99) + C++ (Qt C++11) |
| 平台 | ARM Linux (内核 4.9.88)，Buildroot 交叉编译 |

| UI | Qt 5.12 QWidget + Qt Designer + linuxfb + tslib 触控 |
| 构建 | GNU Make，arm-buildroot-linux-gnueabihf 交叉编译 |

## 各模块详情

### gps_daemon — GPS 定位

- **串口**: `/dev/ttymxc5`，9600bps/8N1，termios 非阻塞配置
- **NMEA-0183 解析**: 字符级状态机 (不使用 sscanf)，支持 6 种语句 ($GPGGA/$GPRMC/$GPGLL/$GPGSA/$GPGSV/$GPVTG)
- **里程累计**: Haversine 公式，过滤 <1m 漂移
- **技术点**: termios raw mode、NMEA 度分→十进制度转换、XOR 校验和、ringbuffer 粘包处理

### dvr_daemon — 行车录像

- **V4L2 采集**: mmap 零拷贝，32 个缓冲区，MJPEG 640x480@15fps
- **MJPEG 直存**: 帧数据已是 JPEG，零编码开销
- **录像控制**: 开始/暂停/继续/停止，录制时长追踪
- **拍照**: 当前帧直接存 JPEG 到 `/record/`，自动编号
- **循环存储**: 60s/段，超限自动删最旧
- **预览**: 每 15 帧写 `/tmp/dvr_preview.jpg`，Qt QTimer 每秒刷新
- **物理按键**: KEY1→拍照, KEY2→暂停/继续 (Qt 按 Tab 分发)
- **技术点**: V4L2 ioctl、poll 多路复用、分段存储、fflush 策略

### av_daemon — 音频播放

- **ALSA PCM**: snd_pcm_open("hw:0,0") → snd_pcm_writei 阻塞写入 (和 aplay 一致)
- **WM8960 混音**: Speaker/Headphone 音量 (非线性映射) + PCM 输出通路开关
- **播放方式**: 整文件 WAV 读入内存，同步播放；自动切下一首
- **控制**: Socket 协议 (PLAY/PAUSE) + 文件方式 (音量 `/tmp/av_volume`，曲目名 `/tmp/av_track`)
- **物理按键**: KEY1→播放, KEY2→暂停 (Qt 按 Tab 分发)
- **技术点**: ALSA lib、WAV RIFF 格式、Mixer 控制、poll 非阻塞响应 UI 指令

### Qt SensorThread — 温湿度

- **驱动**: `/dev/mydht11` 内核字符设备，`read(fd, buf, 2)` 返回 `[湿度, 温度]`
- **Qt QThread**: 独立线程持续循环读，避免 DHT11 驱动 (~230ms/次) 阻塞 UI
- **设备独占**: SensorThread 与 sensor_daemon 二选一，最终方案由 Qt 线程独占读取
- **技术点**: QThread + signal/slot 跨线程更新、DHT11 持续轮询特性

### canbus_daemon — CAN 总线

- **SocketCAN**: `socket(PF_CAN, SOCK_RAW, CAN_RAW)` + bind
- **CAN ID 位操作**: EFF/RTR/ERR 标志位，标准帧/扩展帧
- **错误帧**: TEC/REC 计数器，总线状态监控
- **环形缓冲**: 最近 200 条报文
- **技术点**: can_frame 结构体解析、setsockopt 错误帧过滤、loopback 测试模式

### input_daemon — 按键管理

- **Input 子系统**: `/dev/input/event2` (gpio-keys)，`struct input_event` 读取
- **手势 FSM**: 每按键独立状态机 (短按/长按>2s/双击<500ms)
- **LED 闪烁**: `/dev/100ask_led` 驱动，每次短按亮 150ms 后自动熄灭
- **功能分发**: Qt 根据当前标签页自动分发 — DVR 页 KEY1=拍照 KEY2=暂停，音乐页 KEY1=播放 KEY2=暂停
- **技术点**: input_event 解析、FSM 状态转换、poll 50ms tick 驱动

### guard_daemon — 系统守护

- **进程管理**: fork+exec 启动子进程，SIGCHLD+waitpid 回收，指数退避重启 (60s 窗口内最多 5 次)
- **系统监控**: `/proc/stat`(CPU)、`/proc/meminfo`(内存)、`/proc/loadavg`(负载)、`statfs`(磁盘)
- **守护进程化**: 双 fork+setsid+chdir+umask 标准流程
- **技术点**: daemonize、signalfd、fork/exec/waitpid、/proc 文件系统解析

### qt_ui — 触控界面

- **5 个标签页**: 仪表盘(速度表 QPainter 手绘) / DVR(预览+录像时长+暂停/拍照) / 音乐(播放控制) / CAN(监控+发送) / 温湿度(大字实时数值)
- **5 路 QLocalSocket**: 连接 gps/dvr/av/can/input 后台进程
- **QThread 传感器读取**: 独立线程持续读 `/dev/mydht11`，避免阻塞 UI
- **物理按键分发**: KEY1/KEY2 根据当前标签页自动切换功能 (DVR:拍照+暂停, 音乐:播放+暂停)
- **QPainter 自定义控件**: 速度表半圆仪表盘，彩色弧段+指针
- **Qt Designer .ui 布局** + linuxfb + tslib 触控

## 技术亮点

1. **自定义二进制 IPC 协议**: 帧头 0xAA55 + 消息类型 + 大端长度 + 数据 + 帧尾，零第三方库依赖
2. **跨语言结构体对齐**: C/C++ `#pragma pack(1)` 确保 ARM 32-bit `time_t`(4字节) 与 Qt 端 `uint32_t` 逐字节一致
3. **epoll→poll 迁移**: 开发板内核 timerfd/signalfd 存在兼容问题，全部模块改用 POSIX poll+signal
4. **协议 htons/ntohs 双重反转 bug**: 手动拆分字节时不应再用 htons，否则小端序平台做两次反转。C→C 通信因 ntohs 负负得正没暴露，C→Qt 全坏
5. **设备独占管理**: DHT11/LED 等字符设备驱动只允许单进程打开，Qt SensorThread 独占 `/dev/mydht11`
6. **WM8960 PCM 通路陷阱**: `Left/Right Output Mixer PCM` 开关默认关闭，必须显式打开才有声音
7. **WM8960 音量非线性**: raw 值 0-127 与感知音量不成正比，需自定义映射曲线
8. **DHT11 驱动轮询特性**: 需持续快速 read 才产生有效数据，Qt QThread 无间隔循环读匹配驱动特性
9. **MJPEG 直存**: 摄像头硬件压缩，帧数据直接 JPEG，零软件编码，528MHz 单核流畅运行
10. **memset 与参数别名陷阱**: `dvr_storage_init(&st, st.base_path, ...)` 中 path 与 st->base_path 是同一内存，memset 清零后 strncpy 拷贝空字符串导致录像路径丢失

## 调试过程

端到端调试，解决编译、运行、集成问题 40+ 个。详见 `docs/调试问题记录.md`。

关键教训:
- ARM 32-bit `time_t` ≠ x86 `uint64_t`，跨平台二进制通信必须 `static_assert(sizeof(...))`
- 内核 4.9.88 的 epoll/timerfd/signalfd 存在兼容问题，改用 poll+signal
- htons/ntohs 与手动字节拆分组合使用时，小端序平台会双重反转导致 C→Qt 通信全坏
- `memset(st, 0, ...)` 清零前必须检查参数指针是否指向 st 内部成员
- WM8960 声卡 PCM 输出通路默认关闭，无声音
- DHT11 驱动需持续快速轮询，间歇式采样无法获取数据
